Callbacks y "callback hell"

Un callback es una función que se pasa como argumento a otra función para que se ejecute después. Es la estrategia más antigua de JavaScript para manejar asincronía, y aunque hoy prefieras promesas, entenderlos es esencial porque siguen apareciendo en APIs del navegador y librerías antiguas.

Qué es un callback

En JavaScript las funciones son valores de primera clase: puedes pasarlas como argumento. Un callback es simplemente eso: una función que se entrega a otra para que la llame más tarde, ya sea de forma síncrona o asíncrona.

callback-simple.js 
function saludar(nombre, callback) {
  const mensaje = `Hola, ${nombre}`;
  callback(mensaje);
}

saludar("Ana", console.log); // "Hola, Ana"

Callbacks síncronos vs asíncronos

Los callbacks que usan forEach, map o filter son síncronos: se ejecutan inmediatamente dentro del bucle. Los callbacks de setTimeout, addEventListener o fs.readFile son asíncronos: se ejecutan después, cuando ocurre el evento o la operación termina.

callback-asincrono.js 
function leerArchivo(callback) {
  setTimeout(() => {
    callback(null, "contenido del archivo");
  }, 1000);
}

leerArchivo((err, data) => {
  if (err) return console.error(err);
  console.log(data);
});

El patrón error-first

Node.js popularizó una convención: el primer parámetro del callback es siempre el error (null si todo fue bien) y el segundo son los datos. Esto se conoce como error-first callback y lo usan librerías como fs, readline y muchas otras.

error-first.js 
function dividir(a, b, callback) {
  if (b === 0) {
    callback(new Error("No se puede dividir por cero"));
  } else {
    callback(null, a / b);
  }
}

dividir(10, 2, (err, resultado) => {
  if (err) return console.error(err.message);
  console.log(resultado); // 5
});

Callback hell: la pirámide de la perdición

Cuando necesitas encadenar varias operaciones asíncronas, los callbacks se anidan uno dentro de otro creando una estructura triangular difícil de leer, mantener y depurar. Esto se conoce como callback hell o pyramid of doom.

callback-hell.js 
obtenerUsuario(1, (err, usuario) => {
  if (err) return console.error(err);
  obtenerPedidos(usuario.id, (err, pedidos) => {
    if (err) return console.error(err);
    obtenerDetalle(pedidos[0].id, (err, detalle) => {
      if (err) return console.error(err);
      console.log(detalle);
    });
  });
});

El callback hell no solo es feo: hace que manejar errores sea propenso a omisiones y que reutilizar lógica entre pasos sea tedioso. Las promesas y async/await fueron creadas precisamente para resolver esto.

Alternativas al callback hell

Puedes mitigar el anidamiento extrayendo funciones con nombre, pero la solución real llegó con las promesas (el siguiente tema). Un callback mal escrito puede siempre reescribirse como una cadena de .then() o con await.

extrayendo-callbacks.js 
function onUsuario(err, usuario) {
  if (err) return console.error(err);
  obtenerPedidos(usuario.id, onPedidos);
}
function onPedidos(err, pedidos) {
  if (err) return console.error(err);
  obtenerDetalle(pedidos[0].id, onDetalle);
}
function onDetalle(err, detalle) {
  if (err) return console.error(err);
  console.log(detalle);
}

obtenerUsuario(1, onUsuario);

Aplanar así mejora la legibilidad, pero el flujo sigue siendo difícil de seguir. Por eso el ecosistema migró a promesas, que verás a continuación.
