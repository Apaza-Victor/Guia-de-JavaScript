Rendimiento y optimización

Una aplicación rápida no es un lujo — es una expectativa del usuario. Con técnicas como debounce, throttle, lazy loading y gestión cuidadosa de la memoria, tu código JS puede mantenerse fluido incluso en dispositivos modestos.

Debounce vs Throttle

Ambas técnicas limitan la frecuencia con la que se ejecuta una función, pero con diferencias clave:

  • Debounce: ejecuta la función después de que haya pasado un tiempo sin nuevas llamadas. Ideal para búsqueda en autocompletado.
  • Throttle: ejecuta la función como máximo una vez cada cierto intervalo. Ideal para el evento scroll o resize.
debounce-throttle.js 
function debounce(fn, delay) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

function throttle(fn, limit) {
  let enEspera = false;
  return function (...args) {
    if (!enEspera) {
      fn.apply(this, args);
      enEspera = true;
      setTimeout(() => enEspera = false, limit);
    }
  };
}

const buscar = debounce(texto => fetch(`/api?q=${texto}`), 300);
const alScroll = throttle(() => console.log('Scrolling'), 200);

DebounceEjecuta al final de una ráfagaAutocompletado, validación de formularios
ThrottleEjecuta espaciadamente durante una ráfagaScroll, resize, drag, game loop

Lazy Loading

Cargar recursos solo cuando se necesitan mejora el tiempo de carga inicial. Las imágenes pueden cargarse con el atributo loading="lazy" nativo, y para lógica más compleja usamos IntersectionObserver o import() dinámico.

lazy-loading.js 
// IntersectionObserver
const observer = new IntersectionObserver((entries) => {
  entries.forEach(e => {
    if (e.isIntersecting) {
      const img = e.target;
      img.src = img.dataset.src;
      observer.unobserve(img);
    }
  });
});

document.querySelectorAll('img[data-src]').forEach(
  img => observer.observe(img)
);

// Import dinámico
btn.addEventListener('click', async () => {
  const modulo = await import('./heavy-module.js');
  modulo.ejecutar();
});

Memory leaks

Los memory leaks ocurren cuando el garbage collector no puede liberar memoria porque hay referencias activas que ya no se necesitan. Las causas más comunes son: closures que retienen objetos grandes, event listeners nunca removidos y referencias a elementos del DOM eliminados.

memory-leak.js 
// ❌ Memory leak: event listener nunca removido
function crear() {
  const elem = document.getElementById('btn');
  elem.addEventListener('click', () => {
    console.log(elem); // elem nunca se libera
  });
}

// ✅ Correcto: remover listener cuando ya no se necesita
function crear() {
  const elem = document.getElementById('btn');
  function handler() { console.log(elem); }
  elem.addEventListener('click', handler);
  // En algún punto: elem.removeEventListener('click', handler);
}

Usa las DevTools para detectar memory leaks. La pestaña Memory de Chrome te permite tomar snapshots del heap y compararlos para identificar objetos que no deberían seguir vivos.

requestAnimationFrame

Para animaciones y actualizaciones visuales, requestAnimationFrame es superior a setTimeout o setInterval porque se sincroniza con el ciclo de refresco del monitor (normalmente 60 fps).

raf.js 
let pos = 0;
function animar() {
  pos += 2;
  elemento.style.transform = `translateX(${pos}px)`;
  if (pos < 300) requestAnimationFrame(animar);
}
requestAnimationFrame(animar);
