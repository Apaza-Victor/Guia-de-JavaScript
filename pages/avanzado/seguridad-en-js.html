Seguridad en JS

JavaScript ejecuta código en el navegador del usuario, lo que lo convierte en un vector de ataque muy atractivo. Conocer las vulnerabilidades más comunes y cómo mitigarlas no es opcional — es parte del oficio.

XSS — Cross-Site Scripting

Un ataque XSS ocurre cuando un atacante logra inyectar scripts maliciosos en una página web que otros usuarios van a ejecutar. Se clasifica en tres tipos:

  • Reflejado: el payload va en la URL o en un formulario y se refleja inmediatamente en la respuesta.
  • Almacenado: el atacante guarda el código malicioso en el servidor (ej. un comentario) y se ejecuta al cargar la página.
  • DOM-based: la vulnerabilidad está en el código JavaScript del lado del cliente, no en el servidor.
xss-ejemplo.js 
// ❌ Peligro: innerHTML con datos externos
const nombre = '';
document.getElementById('saludo').innerHTML = nombre;

// ✅ Seguro: textContent escapa HTML automáticamente
document.getElementById('saludo').textContent = nombre;

Nunca confíes en input del usuario. Sanitiza siempre cualquier dato que venga del exterior (formularios, query params, fetch, localStorage) antes de insertarlo en el DOM.

Mitigación de XSS

Las defensas principales contra XSS son: escapar la salida (textContent en vez de innerHTML), usar librerías que sanitizan automáticamente (DOMPurify) y aplicar una Content-Security-Policy estricta.

sanitizar.js 
import DOMPurify from 'dompurify';

const sucio = '
Texto
';
const limpio = DOMPurify.sanitize(sucio);
console.log(limpio); // 
Texto

CORS

Cross-Origin Resource Sharing es un mecanismo del navegador que controla qué recursos pueden solicitarse desde un origen distinto. Cuando haces una petición fetch a un dominio diferente, el navegador envía un header Origin y espera que el servidor responda con Access-Control-Allow-Origin.

cors-headers.js 
// El servidor debe incluir:
// Access-Control-Allow-Origin: https://tusitio.com
// Access-Control-Allow-Methods: GET, POST, PUT, DELETE
// Access-Control-Allow-Headers: Content-Type, Authorization

// Para peticiones simples (GET sin headers personalizados)
// el navegador no envía preflight.

Content-Security-Policy

La CSP es una capa adicional de seguridad que se define mediante un header HTTP. Le dices al navegador qué recursos puede cargar y ejecutar, bloqueando cualquier intento de inyección.

csp-header.txt 
Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.jsdelivr.net;
  style-src 'self' https://fonts.googleapis.com;
  img-src 'self' data:;

Con esta política, el navegador solo ejecutará scripts del mismo origen y de jsdelivr, ignorando cualquier intento de inyectar código desde otras fuentes.
