ESLint y Prettier

Mantener consistencia en un proyecto con varios desarrolladores es imposible sin herramientas automáticas. ESLint atrapa errores antes de que lleguen a producción y Prettier elimina las discusiones sobre formato.

¿Qué hace cada uno?

Aunque a menudo se usan juntos, ESLint y Prettier tienen roles distintos. ESLint analiza el código en busca de errores lógicos y malas prácticas, mientras que Prettier se ocupa exclusivamente del formato: comillas, sangría, saltos de línea, etc.

CaracterísticaESLintPrettier
PropósitoErrores y buenas prácticasFormato automático
Reglas configurablesCientos, muy granularesPocas, intencionadamente limitadas
Corrige automáticamenteAlgunas reglas (--fix)Siempre (reescribe el archivo)
Se integra conEditor, CI, webpack/viteEditor, scripts npm

Configurar ESLint

ESLint se configura con un archivo .eslintrc.json (o .js / .yaml). La configuración más común parte de eslint:recommended y añade reglas específicas del proyecto.

.eslintrc.json 
{
  "env": {
    "browser": true,
    "es2022": true,
    "node": true
  },
  "extends": "eslint:recommended",
  "rules": {
    "no-unused-vars": "warn",
    "semi": ["error", "always"],
    "quotes": ["error", "single"],
    "eqeqeq": ["error", "always"],
    "no-console": "warn"
  }
}

Reglas comunes que marcan la diferencia: no-unused-vars detecta variables que declaraste y nunca usaste, eqeqeq fuerza === en lugar de ==, y no-console te recuerda limpiar los console.log antes de hacer commit.

Configurar Prettier

Prettier se configura con .prettierrc. Sus opciones son pocas a propósito: el proyecto quiere que dejes de pensar en el formato.

.prettierrc 
{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "trailingComma": "all"
}

Para evitar conflictos entre ESLint y Prettier, instala eslint-config-prettier, que desactiva las reglas de ESLint que chocan con Prettier:

terminal 
npm install -D eslint prettier eslint-config-prettier

Luego añade "prettier" al array "extends" de ESLint, siempre al final para que sobrescriba las reglas de formato.

Automatización con Husky y lint-staged

Para asegurarte de que todo el código que llega al repositorio pasa las reglas, usa husky (ganchos de git) con lint-staged (solo archivos modificados):

package.json (fragmento) 
{
  "lint-staged": {
    "*.js": ["eslint --fix", "prettier --write"]
  }
}

ESLint + Prettier en el editor: instala las extensiones correspondientes en VS Code (ESLint y Prettier) y configura "editor.formatOnSave": true. Así cada vez que guardes, el código se formatea solo y los errores se marcan en rojo al instante.

Con ESLint y Prettier activos, tu equipo entero escribe con las mismas reglas sin pensarlo. El siguiente paso es manejar los errores que sí requieren lógica manual.
