Clean Code aplicado a JS

El código se lee muchas más veces de las que se escribe. Aplicar principios de código limpio no es obsesión estética: es la diferencia entre un proyecto que da miedo tocar y uno que da gusto mantener.

Nombres que comunican intención

El primer principio de código limpio es poner nombres que revelen la intención. Una variable llamada d no dice nada; diasRestantes lo dice todo. Lo mismo aplica a funciones: calcularTotal() es mejor que calc(), y enviarNotificacion() es mejor que proc().

nombres-significativos.js 
// Mal
const d = new Date();
const arr = [1, 2, 3];
function pr(x) { console.log(x); }

// Bien
const fechaActual = new Date();
const numerosPendientes = [1, 2, 3];
function imprimirResultado(valor) { console.log(valor); }

Usa nombres pronunciables y buscables. Evita abreviaturas crípticas (usrCtrl) o nombres de una letra fuera de un bucle (i, j están bien en for).

Funciones pequeñas y de una sola responsabilidad

Una función debería hacer una sola cosa y hacerla bien. Si tu función tiene más de 15-20 líneas o puedes describirla con un "y" ("calcula el total y envía el email"), probablemente deberías dividirla.

funcion-responsabilidad-unica.js 
// Mal: hace tres cosas
function procesarPedido(pedido) {
  const total = pedido.items.reduce((sum, i) => sum + i.precio, 0);
  const response = fetch('/api/pagos', { method: 'POST', body: JSON.stringify({ total }) });
  enviarEmail(pedido.usuario, 'Pedido confirmado');
  return response;
}

// Bien: cada función tiene un propósito
function calcularTotal(items) {
  return items.reduce((sum, i) => sum + i.precio, 0);
}

function cobrarPedido(total) {
  return fetch('/api/pagos', { method: 'POST', body: JSON.stringify({ total }) });
}

function procesarPedido(pedido) {
  const total = calcularTotal(pedido.items);
  return cobrarPedido(total);
}

Evitar side effects

Una función que modifica una variable externa o muta un argumento sin avisar genera bugs difíciles de rastrear. Prefiere funciones puras: dado el mismo input, siempre devuelven el mismo output sin modificar nada fuera.

sin-side-effects.js 
// Mal: muta el array original
function agregarItem(lista, item) {
  lista.push(item);
  return lista;
}

// Bien: devuelve un nuevo array
function agregarItem(lista, item) {
  return [...lista, item];
}

Early return y evitar else complejo

El early return reduce la anidación y hace que el flujo normal quede claro al final de la función. Si una función tiene if/else anidados, es señal de que necesita simplificarse.

early-return.js 
// Mal: anidado y confuso
function validarUsuario(usuario) {
  if (usuario) {
    if (usuario.email) {
      if (usuario.email.includes('@')) {
        return true;
      } else {
        return false;
      }
    } else {
      return false;
    }
  } else {
    return false;
  }
}

// Bien: early returns
function validarUsuario(usuario) {
  if (!usuario) return false;
  if (!usuario.email) return false;
  return usuario.email.includes('@');
}

Comentarios que explican "por qué", no "qué"

El código debería explicar por sí mismo qué hace. Los comentarios deben reservarse para el por qué: decisiones de negocio, workarounds por bugs de terceros, razones históricas. Si necesitas un comentario para explicar qué hace una línea, esa línea necesita refactorizarse.

comentarios-utiles.js 
// Mal: comenta el qué
// Multiplica el precio por la cantidad
const total = precio * cantidad;

// Bien: comenta el por qué
// El descuento del 10% solo aplica en campaña de verano
const descuento = esCampanyaVerano ? 0.1 : 0;

Principios SOLID en JS: aunque SOLID nació para la POO clásica, sus principios se aplican muy bien en JavaScript. El más útil en el día a día es el Principio de Responsabilidad Única (SRP): una clase o función debe tener una sola razón para cambiar. Los otros cuatro (Open/Closed, Liskov, Segregación de Interfaces, Inversión de Dependencias) aparecen cuando empiezas a diseñar sistemas más grandes con clases o módulos.

Consistencia por encima de todo

Da igual si prefieres comillas simples o dobles, punto y coma o no, espacios o tabs: lo importante es elegir una convención y mantenerla en todo el proyecto. Para eso existen herramientas como ESLint y Prettier, que veremos en el siguiente tema.
