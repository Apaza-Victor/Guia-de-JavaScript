Testing básico

Los tests no son un lujo ni algo que se añade al final. Son la red de seguridad que te permite refactorizar sin miedo y la documentación viva de lo que tu código debería hacer.

¿Por qué testear?

Un test automático verifica que un fragmento de código se comporta como esperas. Sin tests, confías en que "funciona porque lo probé a mano". Con tests, tienes una suite que puedes ejecutar en segundos y que detecta si algo se rompe después de un cambio. En proyectos de más de un desarrollador o que evolucionan con el tiempo, los tests son tan importantes como el código de producción.

Jest y Vitest

Jest es el framework de testing más popular para JavaScript. Vitest es su competidor moderno, diseñado para proyectos con Vite, con una API casi idéntica. Ambos comparten la misma sintaxis básica: describe para agrupar, it o test para cada caso, y expect para las aserciones.

suma.test.js 
function sumar(a, b) {
  return a + b;
}

describe('sumar', () => {
  it('suma dos números positivos', () => {
    expect(sumar(2, 3)).toBe(5);
  });

  it('suma un número negativo y uno positivo', () => {
    expect(sumar(-1, 5)).toBe(4);
  });
});

Matchers comunes

Los matchers son los métodos que usas sobre expect para verificar valores. Cada uno está pensado para un tipo de aserción distinto.

MatcherQué verificaEjemplo
toBe()Igualdad estricta (===)expect(1 + 1).toBe(2)
toEqual()Igualdad profunda (objetos/arrays)expect({a:1}).toEqual({a:1})
toBeTruthy()Valor truthy en booleanoexpect('hola').toBeTruthy()
toBeFalsy()Valor falsyexpect(0).toBeFalsy()
toContain()Un array contiene un elementoexpect([1,2,3]).toContain(2)
toThrow()Una función lanza un errorexpect(() => f()).toThrow()
matchers-ejemplos.test.js 
describe('matchers útiles', () => {
  it('toEqual para objetos', () => {
    const obj = { nombre: 'Ana', edad: 30 };
    expect(obj).toEqual({ nombre: 'Ana', edad: 30 });
  });

  it('toContain en arrays', () => {
    const frutas = ['manzana', 'pera', 'uva'];
    expect(frutas).toContain('pera');
  });

  it('toThrow para errores', () => {
    const lanzarError = () => { throw new Error('fail'); };
    expect(lanzarError).toThrow('fail');
  });
});

Setup y teardown

Cuando varios tests necesitan el mismo estado inicial, usa beforeEach / afterEach (o beforeAll / afterAll). Así evitas repetir código y cada test parte de un estado conocido.

setup.test.js 
let usuarios;

beforeEach(() => {
  usuarios = [];
});

it('agrega un usuario', () => {
  usuarios.push('Ana');
  expect(usuarios).toContain('Ana');
});

it('empieza vacío cada test', () => {
  expect(usuarios).toHaveLength(0);
});

Mocks básicos

Un mock reemplaza una función real para controlar su comportamiento y verificar que fue llamada con los argumentos esperados. jest.fn() es la forma más simple.

mock.test.js 
const enviarEmail = jest.fn();

function registrarUsuario(email, notificar) {
  notificar(email);
  return { email, registrado: true };
}

it('llama al callback de notificación con el email', () => {
  const resultado = registrarUsuario('ana@test.com', enviarEmail);
  expect(enviarEmail).toHaveBeenCalledWith('ana@test.com');
  expect(resultado.registrado).toBe(true);
});

TDD vs test después: TDD (Test-Driven Development) propone escribir el test antes que el código. No es obligatorio, pero tiene una ventaja: te obliga a pensar en el diseño y el contrato de la función antes de implementarla. Si recién empiezas con tests, escribir los tests después de tener el código es un buen punto de partida. Lo importante es que existan.

Saber testear te da confianza para refactorizar, y es el prerrequisito para integrar herramientas de CI/CD. Pero cuando un test falla y no entiendes por qué, el debugging entra en juego.
