Git aplicado a proyectos JS

El código que no está versionado no existe. Git es el estándar indiscutible, y saber usarlo bien en un proyecto JavaScript marca la diferencia entre un historial útil y un caos de commits.

.gitignore para proyectos JS

No todo lo que está en tu carpeta debe ir al repositorio. El archivo .gitignore le dice a Git qué archivos ignorar. En un proyecto JavaScript típico, al menos estos:

.gitignore 
node_modules/
dist/
.env
.env.local
*.log
.DS_Store
coverage/
.cache/

node_modules es el más obvio: no tiene sentido versionar las dependencias, se instalan con npm install. .env contiene claves y secretos que nunca deben subirse. dist/ es la salida del build, que se genera en cada despliegue.

Commits semánticos (Conventional Commits)

Un commit bien escrito cuenta una historia. El formato Conventional Commits estandariza los mensajes para que sean legibles tanto por humanos como por herramientas automáticas (generación de changelogs, versionado semántico).

ejemplos-de-commits 
feat: añadir validación de email en el formulario de registro
fix: corregir error al calcular descuento con IVA incluido
docs: actualizar README con instrucciones de instalación
refactor: extraer lógica de pagos a servicio separado
test: agregar tests unitarios para la función calcularTotal
chore: actualizar dependencias

La estructura es: tipo(ámbito opcional): descripción. Los tipos más usados son feat (nueva funcionalidad), fix (corrección de bug), docs (documentación), refactor (cambio que no añade funcionalidad ni corrige bugs), test (tests) y chore (tareas de mantenimiento).

Conventional Commits + versionado semántico: si usas Conventional Commits, herramientas como standard-version o semantic-release pueden determinar automáticamente si el próximo release es major, minor o patch según los commits. fix incrementa patch, feat incrementa minor, y un BREAKING CHANGE incrementa major.

Flujo de trabajo con ramas

En un proyecto individual puedes trabajar solo en main, pero en equipo — o incluso solo para organizarte mejor — conviene usar ramas. Un flujo simple y efectivo:

  • main — la rama de producción. Solo recibe merges desde otras ramas.
  • dev — integración de funcionalidades en desarrollo.
  • feature/nombre — cada nueva funcionalidad en su propia rama, que se mergea a dev al terminar.
  • fix/nombre — lo mismo para correcciones.
flujo-basico.sh 
git checkout -b feature/validar-email
# trabajas, haces commits…
git add .
git commit -m "feat: añadir validación de email"
git checkout dev
git merge feature/validar-email
git push origin dev

Comandos esenciales del día a día

Más allá del add/commit/push, hay comandos que salvan el día:

  • git log --oneline --graph — historial compacto con árbol de ramas.
  • git diff — cambios sin staged.
  • git stash — guarda cambios temporalmente para cambiar de rama.
  • git pull --rebase — integra cambios remotos sin un merge commit extra.
